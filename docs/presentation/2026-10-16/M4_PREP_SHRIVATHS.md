Study your own stage. Read sections 1–5 first, practise the board explanation, then rehearse the questions. Darshan narrates the report slide during the flash talk; you answer technical questions about M4. You do not need to study the other stages beyond knowing that they supply the transcript.

## 1. Your job in one sentence

**“My stage reads the speaker-attributed transcript and produces a structured report using a local LLM, while preserving the original speaker labels and timestamps.”**

**Input:** Stage-3 transcript JSON containing words, speaker labels and times. **Output:** `report.md` and `report.json`, with summary, topic, key points, keywords, dialogue and an action-item section.

The stage produces a report, but its measured transcript repair does not improve accuracy. The action-item section contains no accepted actions in the evaluated reports. These limits are part of your result.

## 2. ELI5: an editor with restricted permissions

Imagine giving an editor a rough transcript. The editor can suggest cleaner text, translate lines and summarise the discussion. It cannot listen to the original recording, so it cannot reliably recover words the recogniser never heard.

The software keeps the original text and checks the editor's suggestions. Some changes are rejected. Speaker names and times are copied through rather than accepted from the model's response.

These restrictions protect structure, not truth. A grammatically fluent translation can still be wrong, and a summary can repeat an upstream recognition error.

## 3. The actual path through your code

### A. Run the local model

The repo uses **AI4Bharat Airavata 7B**, quantised to **Q4_K_M**, through a local **llama.cpp server**. The Python client calls its OpenAI-compatible HTTP interface. This interface does not mean the report is generated by a hosted OpenAI model.

Quantisation reduces the memory required for weights. The 4-bit model fits the laptop's 6 GB GPU for a separate Stage-4 pass. The repository does not train Airavata, and it does not claim that quantisation improves accuracy.

### B. Split the transcript into chunks

`PostProcessor._plan_chunks` respects the available token budget and a default maximum of **six lines per chunk**. A line contains its text plus speaker/time context. The prompt asks for line repair, English translation, uncertainty and chunk-level information.

This is a **two-phase workflow**, not necessarily two API calls: several chunks may each require a call, followed by synthesis. The saved demo uses four LLM calls. Retries or long inputs can require more.

### C. Constrain the response structure

`chunk_schema` specifies the expected line IDs in order. The llama.cpp server can enforce that JSON structure through grammar-constrained generation. The reply does not supply authoritative speaker or time fields; the code copies those from the input.

Structure enforcement prevents certain malformed outputs. It cannot force a correct translation. The code still validates returned content and handles failures defensively.

### D. Check suggested edits

`_check_chunk` compares proposed text with the original. The implementation reverts excessive character changes, excessive word additions, disallowed word drops and replacement of protected English loanwords. The default maximum character edit ratio is **0.5**. The addition threshold permits up to `max(1, round(0.2 × source_word_count))` extra tokens before this particular check rejects the line; do not describe it as a blanket ban on every added word.

Other checks flag overly long English translations and drop a repeated identical English translation attached to different source lines. Missing/unusable lines keep or recover the ASR text with diagnostics. Failed chunks can be halved and retried.

### E. Build the report and filter claims

The synthesis phase produces title, topic, summary, key points, keywords and actions. Keywords undergo a lexical grounding check. Actions need a valid owner and supporting evidence references/words. These checks are imperfect proxies for factual correctness.

The report's Hinglish column is generated by the existing romaniser from the retained/repaired Devanagari. It is not freely written by the LLM. The original Stage-3 transcript remains separately available.

## 5. What the results mean

Stage 4 processes four input versions of each of 63 conversations, giving **252 reports**. The versions are the true transcript, ASR on clean voices, ASR on noisy mixture, and the full-pipeline transcript.

| Input | Pooled cpWER before | Pooled cpWER after | Mean paired change |
|---|---:|---:|---:|
| True transcript | 0.0% | 1.9% | +2.0 points |
| ASR on clean voices | 18.0% | 19.1% | +1.2 points |
| ASR on noisy mixture | 30.6% | 31.4% | +0.9 points |
| Full pipeline | 51.8% | 52.8% | +0.9 points |

**cpWER** counts word errors in speaker-specific streams after the best speaker matching. A positive repair change means worse output. Full-pipeline repair helps one conversation and hurts 50; the remaining 12 are unchanged by that score.

The slide's **+0.9 points** is the mean of per-conversation changes (about +0.94 unrounded), with reported conversation-bootstrap interval +0.8 to +1.1. Pooled rates weight by reference word counts, so subtracting the rounded pooled numbers gives 1.0 rather than 0.9. Those are different aggregates.

The full-pipeline baseline here is **51.8%**, not 49.5%, because Stage 4 excludes group 7. Never add 0.9 directly to the separate 72-conversation headline score.

**No accepted action items remain in the 252 reports.** The raw evaluation records four unsupported proposals that were dropped. Thus “never proposed any actions” would be inaccurate.

The “keywords really said” score is 98.8% from the true transcript and 60.5% from full-pipeline text. It checks lexical support against the reference/translation; it is not a human judgement that every keyword has the right meaning. Word overlap between summaries is also a proxy, not a complete summary-quality metric.

Conversations share seven speaker groups, so conversation-level uncertainty intervals can be optimistic. Avoid claiming broad real-world reliability from this sample.

## 7. Likely questions and short answers

**Why keep the LLM when repair makes things worse?** The proposal asks for a structured translated report, which the stage generates. Evaluation shows that its correction and action-extraction goals are not achieved. We preserve the original transcript and disclose the limitation.

**Can it hallucinate?** Yes. It can mistranslate and summarise incorrectly despite valid JSON and unchanged timestamps. The saved demo contains examples.

**Can it change the speaker identity or timestamp?** Those output fields are copied from the input by code. That preserves existing labels; it does not repair upstream diarization mistakes.

**Do guardrails prove the keywords were really said?** They check lexical support, not semantic correctness. A word can occur in a different sense. The demo's “e-pass” mistake illustrates that weakness.

**Why did the action list stay empty?** The evaluated system retained no supported actions. Four proposed actions were rejected. We have not established that a different model or prompt would solve it on held-out data.

**Why six lines per chunk?** The repo documents translation alignment problems with larger chunks and a prompt revision using group 7. That group is excluded from the reported Stage-4 evaluation.

**Did you tune on test data?** Group 7 was used for prompt development and then excluded from Stage-4 scoring. State that explicitly; do not claim that no test-labelled data was ever inspected.

**Does local mean no internet is ever needed?** Inference runs locally after setup. Initial model downloads are separate. The flash talk uses already saved outputs.

**Can all stages run together in 6 GB?** The documented laptop workflow runs Stage 4 separately because its model does not fit alongside Stages 1–3. Do not promise simultaneous residency.

**Why not a larger model?** A larger model is a proposed experiment, subject to resources. The compatible interface makes replacement possible, but no larger-model result is saved in the repo.

**What if the server fails?** The implementation reports failure and retains the earlier-stage results. A failed request is not evidence of a successful report.

**What would prove improvement?** Rerun the same evaluation on appropriately held-out transcripts, compare repair errors and supported actions, and inspect factual correctness. This is a proposed validation approach, not a completed result.
